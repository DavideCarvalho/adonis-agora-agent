'@adonis-agora/agent': minor

Security: the federated console's Redis channel is authenticated, governance writes need a write-level grant, MCP sessions are bounded and bound to their caller, and thread ids are validated before they reach a header (reported privately).

**Breaking:**

- Console commands are authenticated. Before, anyone who could publish on the app's Redis could approve or reject any pending tool call as any approver, or rewrite model prices.
  - **Together with `@adonis-agora/crypto`: nothing to configure.** When crypto is booted in the app (its `agora.crypto` binding), commands are sealed with the crypto key `console-agent` (`aes256-gcm`, in the owning app's partition), created at boot where crypto is embedded. The Hub (crypto embedded) encrypts for each `dashboard.apps` entry's `partition` (default: its key); a console that is a crypto tenant seals through its crypto channel (`crypto:seal:console-*`). No grant is needed on the app side (an app opens its own `console-*` keys); a crypto-tenant app checks its key at boot and logs one info line when it is missing (the crypto server creates it on the console's first command).
  - **Together with authkit:** when authkit's calls between apps are configured (`authkit.client`), each command also carries an app-call token for the owning app, verified there (audience-bound: the partition rule does not apply; the console app's capabilities, e.g. `agent:console:*`, cap the command). With that automatic verifier a crypto command without a token is still accepted, and one with a token must pass it; only explicit `crypto` + explicit `verifyTenant` makes the token mandatory (token mode without crypto always requires it).
  - Explicit modes, used as given (nothing automatic added on top): `crypto: { cipher, key?, owns? }` (any cipher, `owns` for a non-Agora ciphertext format), token mode (`controlPlane.token` + `publicKey` sealed to the app's `APP_KEY`-derived key printed by the new `node ace agent:console-key`; `consoleCommands.verifyTenant`), or the same `secret` on both sides. `crypto: false`, `token: false` and `verifyTenant: false` turn one automatic piece off. The default crypto key is `console-agent` (was `agent-console`).
  - A web process now fails to boot when `consoleCommands` resolves no mode, or a `dashboard.apps` entry may take actions without one; the error names the line to add. `dashboard.apps.<app>.actions: false` (new) makes an app browse-only (no `controlPlane` needed; actions answer `403`, the selector shows `actions: 'none'`). Ace commands never fail on it.
- `consoleCommands.actions` (new) defaults to `false`: approvals and price changes from another console are refused with a `403` until it is `true`.
- A command without capabilities is refused (`403`, code `capabilities-required`), in token mode too: the token never decides alone. The console sends the viewer's capabilities: what its `authorize` returns as `capabilities` (new on the shared result), narrowed to the agent's set, or the full set when it returns none; `access: 'read'` sends none. `agent:console:write` (and `agent:console:*`, `agent:*`, `*`) covers `agent:approvals:decide` and `agent:pricing:write`.
- `authorizeByToken` grants read access only by default: its holder (an MCP client, a scraper) reads every governance table but `POST /agent/governance/pricing`, approvals sent to a federated app, cross-actor approve/reject/cancel and MCP action tools answer `403`. Pass `authorizeByToken({ token, access: 'write' })` for a token that may change things. Every console `authorize` now receives `{ action: 'read' | 'write' }` as its third argument and may answer `{ allowed: true, access: 'read' }`; `anyAuthorize` sends a change to the first authorizer that grants writing.
- MCP sessions (not stateless) are bound to the caller that opened them (another token's request on the id answers `403`), capped per caller (`sessions.maxPerPrincipal`, default 16; the least recently used one is closed) and per endpoint (`sessions.max`, default 1000; `initialize` then answers `503`), and closed after `sessions.idleTimeoutMs` (default 30 minutes) unused; an unknown or expired session id answers `404` (was `400`).
- `POST /agent/chat` and the A2UI route answer `400 invalid_thread_id` for a `threadId` that is not 1-200 letters, digits or `_ - . : @`; the `X-Agent-Thread-Id` header is only written for a valid id.

Commands over a minute old are refused, a replayed command runs once, and answers are authenticated in every mode (a forged answer is ignored). A refused token answers `401` and the console fetches a new one. `node ace agora:doctor` gains `agent.console-commands` (the mode each side resolved; an error when one cannot authenticate) and, with `--deep`, `agent.console-commands-key` (probes the crypto key).

The viewer's grant from the console's `authorize` (`capabilities`, `access: 'read'`) also narrows the console's own app: a price change or a cross-actor approval the viewer's grant does not hold answers `403` ("the viewer lacks …"), and the console's pages disable it (`/governance/apps` now answers `viewer: { capabilities }`). On the app side, explicit `crypto` / `secret` keep the automatic authkit token check (a sent token is verified and caps the command) and, with an `APP_KEY`, token mode beside them; only `verifyTenant` replaces it. The app's partition option is `consoleCommands.partition` (default `prefix`). A crypto-tenant app that cannot create or check the key logs the `crypto:keys:create` line to run and checks again on the first command that fails to open; boot logs go through the app's logger. The console `authorize` contract is the shared Agora one (`allowed`, `apps`, `tenants`, `capabilities`, `access`; a malformed `capabilities` allows nothing); `{ allowed: true, access: 'write' }` is now kept as given.

Checks run in one order: capabilities present (`capabilities-required`, also with `actions` off) → token → viewer → partition → actions; the console aliases (`*`, `agent:*`, `agent:console:*`, `agent:console:write`) are matched literally, a trailing-`*` grant in the agent's namespace covers its branch (`agent:pricing:*`), and a `*` anywhere else grants nothing. The console adds the automatic authkit token beside an explicit `crypto` too. A crypto-tenant app checks its key with a decrypt probe (no `crypto:keys:read` needed) and logs one line when it is missing or cannot be checked. The app side's authentication is resolved, and a misconfiguration thrown, in `boot()`; log lines use the app's logger and the `[@adonis-agora/agent]` prefix.

Uniform wording with every Agora lib: boot failures throw the exported `ConsoleAuthConfigError`; boot logs name each mode (`crypto (auto, key console-agent)`, `token checked when sent (authkit app-call, auto)`, `secret`…) and end with `; actions on` or `; actions off (…)`; token mode names only the app key's short id (the key itself no longer appears in the log; `node ace agent:console-key` prints it); a command nobody answers reports `no instance of "<app>" answered within <n>s — the app may have refused the command (…)`. A garbage message on the command channel is dropped and logged once per reason, never crashing the process.

authkit's key directory: in token mode the app publishes its `APP_KEY`-derived command public key under `console:agent` at boot (when authkit-client offers `publishAppKey`), and a console with no explicit `controlPlane.publicKey` reads it with `appKey` — authkit without crypto is zero-config too. An explicit `publicKey` still wins; an app missing from the directory answers the action `503` with what to do.

Refused commands are logged once per uniform reason (`refused a command (bad signature)`, `(stale)`, `(token refused)`, `(capabilities-required)`, `(mode not accepted here (…))`…); token mode names the key's 8-character id on the app; a console reading it from authkit's directory logs `sealed to the key the app publishes` and fetches it on the first command (boot never depends on authkit); `replayed` is logged only by the instance that already ran that command id; the Hub logs the crypto keys it creates; the doctor prints the boot log's sentences. MCP's session sweeper, like the console channel, runs only in web processes: an ace command opens no timer or connection of the agent's.

Mixed Hubs (crypto apps and authkit-only apps behind one console) need no lines: each app's mode is chosen on its first command — token when the app publishes a key in authkit's directory (it does only when token mode is its only way to be reached), else crypto — cached 5 minutes and chosen again after a failed command. In crypto mode the app-call token is optional: a failed mint sends the command crypto-only with one warning naming the grant to add, retried after 5 minutes. APP_KEY is read from `config/app.ts`, then `config/encryption.ts`'s default entry, then `APP_KEY`. The boot error mentions authkit-client's `service`. The tenant key check uses crypto's `hasKey` when available (no audit noise), falling back to the decrypt probe.
