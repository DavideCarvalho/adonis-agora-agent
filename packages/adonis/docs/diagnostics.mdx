The agent publishes structured telemetry as it runs: **point events** for lifecycle moments, and **spans** for the operations worth timing. Both are opt-out (`emitDiagnostics: false`) and both are inert when [`@adonis-agora/diagnostics`](/docs/diagnostics) is not installed — the package holds no import of it.

They feed the [Telescope "Agent" tab](/docs/agent/governance/telescope), but nothing stops you subscribing directly: pipe them to OpenTelemetry, alert on a failure rate, or log a run's shape during a debugging session.

## Subscribing

Install the peer, then subscribe by library or by exact event:

```ts title="start/agent_diagnostics.ts"
import { onDiagnostic } from '@adonis-agora/diagnostics'

// Every agent event.
onDiagnostic('agent', (event) => {
  logger.debug({ event: event.event, payload: event.payload }, 'agent')
})

// One event.
onDiagnostic('agent', 'run.finished', (event) => {
  metrics.increment('agent.runs.finished')
})
```

Both forms return an unsubscribe thunk. On the wire the channel names are `agora:agent:<event>`.

## The events

Ten names, each with a fixed payload shape.

### `run.started`

Fires at the top of a turn, before the quota check.

```ts
{ runId: string; threadId: string; actorId: string; persona?: string }
```

It is published outside any checkpoint, so a [durable](/docs/agent/durability/durable-runner) run publishes it again each time it replays (a resume after an approval or a question). Count runs from their endings — `run.finished`, `run.failed`, `run.cancelled` — not from this.

### `message`

Fires when an assistant message is persisted.

```ts
{ runId: string; threadId: string; role: 'user' | 'assistant'; textLength: number }
```

<Callout type="info" title="Only `role: 'assistant'` is ever emitted">
The type allows `'user'`, but the loop publishes only the assistant side. If you are counting messages from this event, you are counting replies.
</Callout>

### `tool-call`

Note the hyphen — it is `tool-call`, not `tool.call`. Fires once per tool call, after it settles.

```ts
{
  runId: string
  toolCallId?: string
  toolName: string
  toolType: 'read' | 'action'
  status: string
  durationMs?: number
  replayed?: true
}
```

- `status` is `'executed'`, `'failed'`, or `'rejected'` (a HITL denial, or an approval that expired).
- `toolCallId` is the call's id, the same on every publication of it — key on it to deduplicate.
- `durationMs` is how long the tool ran, measured inside its `tool:<callId>` checkpoint. It is set only when this process ran the tool; a decision (`rejected`) or an `ask` has none.
- `replayed: true` marks a call whose checkpoint the durable runtime read back from its journal instead of running the tool. The attempt that ran it already published it, so **skip these when counting** calls. The same `durationMs` is stored on the call's row as `execution_ms`.

### `run.finished`

Fires once, when the turn completes.

```ts
{
  runId: string
  threadId: string
  steps: number
  inputTokens: number
  outputTokens: number
  durationMs?: number // turn start → end
  ttftMs?: number // turn start → first non-empty `text` frame on the stream
  costUsd?: number // sum of the steps whose cost is known; absent when none was
  modelId?: string // the last model call's model
  queueMs?: number // enqueue → the body starting in a worker (see below)
  modelMs?: number // every `llm.turn`, summed
  toolsMs?: number // tool time, wall-clock: tools a step ran in parallel count once
  modelCalls?: number
  toolCalls?: number
  stepTimings?: StepTiming[] // { step, modelMs?, tools: { toolCallId, toolName, ms }[], toolsMs }
  // AgentRunContext — who and what the run is:
  agentName?: string
  actorId?: string
  tenantRef?: string
  parentRunId?: string // set on a delegation's child run: not a turn of its own
}
```

`ttftMs` is the time to first token as the reader sees it: a frame an output gate held back counts when it was released. It is absent when the turn streamed no text. Both timings use the clock of the process running the turn, so a run resumed elsewhere measures from its resume. `ttftMs` and `modelId` are also stored on the run's row (`ttft_ms`, `model_id`) for the [read-model](/docs/agent/governance/read-model).

### `run.failed`

Fires when the loop throws.

```ts
{
  runId: string; threadId: string; code: AgentStreamErrorCode; durationMs: number
  queueMs?: number
  // what the run measured before it failed — same names as on run.finished:
  modelMs?: number; toolsMs?: number; modelCalls?: number; toolCalls?: number; stepTimings?: StepTiming[]
} & AgentRunContext
```

`code` is the same stable code the stream's `error` frame carries — `quota_exceeded`, `output_rejected`, `structured_output_invalid`, `replay_diverged`, `model_no_output`, or `run_failed` for anything else — and is stored on the run's row as `error_code`. The error itself is **never** on the event. A durable control-flow signal (suspending on an approval or a question, continue-as-new) is not an ending and publishes nothing. A failure the durable engine retries can publish more than once for the same run — key on `runId`.

### `run.cancelled`

Fires when the run's abort signal fired — someone pressed Stop — before it finished.

```ts
{ runId: string; threadId: string; durationMs: number; queueMs?: number } & AgentRunContext
```

### Where a run's time goes

`run.finished` breaks the turn down, and the same figures are stored on the run's row (`queue_ms`, `model_ms`, `tools_ms`, `model_calls`, `tool_calls`, and the per-step list in `timings`) for the [read-model](/docs/agent/governance/read-model) and the dashboard's run trace. None of it is a new clock — each number is one the stack already measures:

- **Queue** — from the run being enqueued to its body starting. Under the [durable runner](/docs/agent/durability/durable-runner) it is `@adonis-agora/durable`'s own record: the run row's `createdAt`, stamped when `engine.start` (or a parent's `ctx.child`, or the queue's `ctx.startChild`) enqueued it, read once on the body's first execution. So it is the enqueuing process's clock against the worker's; skew between them shows up here. Inline there is no queue, and it is about `0`. Stored when the run starts, so a failed or cancelled run has it too.
- **Model** — each step's `llm.turn` span: the span's own duration, journaled with the step's model result.
- **Tools** — each executed call's `tool.execution` time (the same figure as `agent_tool_call.execution_ms`), journaled with the call's persist checkpoint. A step's tool time is the union of its calls' windows, so calls that ran in parallel count once. Approval waits are not tool time, and a delegation's time is its child run's own.

The rule that keeps spans from repeating on a durable replay keeps these from double counting: a figure is measured only inside the step that runs, and written into that step's journal entry. A replay reads it back instead of measuring again. So a **resumed run** — parked on an approval, picked up by another worker — reports every step once, whichever slice ran it, and the time it spent parked is in none of the totals; it is the difference between `durationMs` on the row (start to finish, wall-clock) and queue + model + tools. A step journaled by a release before these figures existed contributes nothing to them. Timings are written to the row on completion; a failed or cancelled run's row has its queue time only, while `run.failed` still carries what it measured before failing. The field names (`queueMs`, `modelMs`, `toolsMs`, `modelCalls`, `toolCalls`, `stepTimings`) are stable — safe to map to metric attributes.

<Callout type="info" title="Endings outside the loop are not published">
`run.failed` and `run.cancelled` come from the loop. A run the dead-run reaper settles, or one cancelled from another process without its loop unwinding here, gets the row update but no event.
</Callout>

### `usage.recorded`

Fires once per row written to the usage ledger: every model call an agent turn makes (its `chat` steps, a structured-output pass, a history summary, a retrieval embedding) **and** every row an app records through [`AgentService.recordUsage`](/docs/agent/governance/quota-and-cost#recording-usage-outside-agent-turns) — so one subscription sees all AI spend. Published after the write succeeds, from inside the step that writes it, so a durable replay never publishes a row twice. No other event carries per-call usage (`run.finished` has the run's totals, not its rows), so this is not a duplicate of anything.

```ts
{
  actorRef: string        // who pays; '@platform' for platform cost
  feature: string         // 'agent:<name>' (or 'agent') for an agent turn, the app's own otherwise
  purpose: string         // 'chat' | 'structured_output' | 'summary' | 'embedding' | … | 'external'
  modelId: string
  provider?: string
  inputTokens: number
  outputTokens: number
  cacheReadTokens?: number  // subsets of inputTokens
  cacheWriteTokens?: number
  audioSeconds?: number
  characters?: number
  requests?: number
  costUsd?: number
  costSource?: 'provider' | 'estimate'
  threadId?: string
  runId?: string
  tenantRef?: string
}
```

Amounts and attribution only. A row's `metadata` is never on the event, and neither is any text.

### `delegated`

Fires when an orchestrator hands work to another agent. A *denied* delegation does not emit this — see [Authorizing a delegation](/docs/agent/authoring/personas-and-agents#authorizing-a-delegation).

```ts
{ runId: string; fromAgent?: string; toAgent: string }
```

### `retrieved`

Fires once per inject-mode retrieval.

```ts
{ runId: string; queryLength: number; count: number }
```

`count: 0` is a zero-hit retrieval — the signal behind the Telescope RAG panel's zero-hit rate.

### `tool.retry`

Fires once per [transient retry](/docs/agent/authoring/transient-retry) — on the attempt that *failed and is about to be retried*, not on the final outcome.

```ts
{ runId: string; toolName: string; toolCallId: string; attempt: number; message: string }
```

### `quota.exceeded`

```ts
{ actorId: string; usedTokens: number; limitTokens: number }
```

<Callout type="warn" title="Never emitted today">
This one is part of the typed contract but the loop does not publish it — it throws `QuotaExceededError` without emitting. Do not build an alert on it: an over-budget turn shows up as a `run.failed` with `code: 'quota_exceeded'`.
</Callout>

## What is redacted, and why

Every payload above carries **lengths and counts, never content**. `message` carries `textLength`, not the text. `retrieved` carries `queryLength`, not the query. `tool-call` carries the name and status, not the input or output. `run.failed` carries the stable `code`, not the error message.

This is not squeamishness: diagnostics are the least-guarded surface in the stack. They fan out to log aggregators, APM vendors, and a browser-facing dashboard, all of which sit outside whatever access control the conversation itself has. A prompt or a tool result routinely carries exactly the data your governance layer exists to protect, so the safe default is that it never leaves the loop through this channel. The full content is in the [governance read-model](/docs/agent/governance/read-model), behind the gate.

`tool.retry` is the one exception: it carries the failed attempt's error `message`, because a retry you cannot diagnose is not worth recording. Tool error messages are yours, so keep them free of caller data if that matters to you.

## Spans

Four operations are traced with a full span lifecycle over `node:diagnostics_channel`:

| Channel | Start payload | End result |
| --- | --- | --- |
| `agora:agent:turn` | `{ runId }` | `{ textLength }` |
| `agora:agent:llm.turn` | `{ runId, step }` | `{ modelId?, inputTokens, outputTokens, textLength, toolCalls }` |
| `agora:agent:tool.execution` | `{ runId, toolCallId, toolName, toolType }` | `{}` |
| `agora:agent:retrieval` | `{ runId, queryLength, topK }` | `{ count }` |

Each publishes on five sub-channels — `:start`, `:end`, `:asyncStart`, `:asyncEnd`, `:error` — carrying an envelope with `v`, `ts`, `lib`, `event`, `phase`, `spanId`, `traceId`, and a phase-specific field (`payload` on start, `durationMs` on end, `result` on `asyncEnd`, `error` on `error`).

**`traceId` is always the `runId`**, so every span from one turn groups without any correlation work. Duration lands on `asyncEnd` (or `error`), which is the phase to read for timing.

`tool.execution` wraps the whole invocation *including* its transient retries, so its duration is wall-clock cost to the run, not the cost of the last attempt. Its result is deliberately empty — tool output never rides a span, for the reason above.

Spans are **zero-cost when nobody is listening**: with no subscriber on any sub-channel, the operation runs with no span id allocated and no publish. Subscribe with the raw builtin if you want them without the diagnostics package:

```ts
import diagnostics_channel from 'node:diagnostics_channel'

diagnostics_channel.subscribe('agora:agent:llm.turn:asyncEnd', (message) => {
  otelHistogram.record(message.durationMs, { model: message.result?.modelId })
})
```

<Callout type="info" title="Spans and durable replay">
Spans are emitted from inside memoized steps, which durable replay skips — so a replayed run does not re-emit spans for work it is not redoing. One consequence: under the [durable runner](/docs/agent/durability/durable-runner) there is no root `turn` span, because a turn spans multiple replay slices. Group by `traceId` instead.
</Callout>

## Turning it off

```ts title="config/agent.ts"
export default defineConfig({
  emitDiagnostics: false,
})
```

The default is `true`, and it is already a no-op when the diagnostics package is absent, so there is rarely a reason to set it. Do it if you have the package installed for another library and want the agent to stay quiet.
