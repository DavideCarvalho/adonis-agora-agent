The provider mounts eleven core routes under `config.path` (default `agent`) at boot. They cover the full chat lifecycle — start, stream, cancel, HITL, threads, and quota. No controllers to write; the provider resolves the actor, calls the framework-agnostic `AgentService`, and pipes the SSE.

**Five optional surfaces** mount only when their configuration is present:

| Surface | Mounts when |
| --- | --- |
| `POST /agent/attachments` | `attachmentStaging` is set — see [Attachments](/docs/agent/authoring/attachments). |
| `GET /agent/approvals/mine` | a governance read-model resolves. Not behind `governanceAuthorize`; always scoped to the caller. |
| `/agent/governance/*` (11 routes) | a read-model resolves **and** a `governanceAuthorize` gate is configured. Without the gate they are **not mounted at all** and answer `404` — see [Governance read-model](/docs/agent/governance/read-model). |
| `GET\|POST /agent/governance/pricing` | the above, **plus** a `pricingStore`. |
| `POST\|GET\|DELETE /mcp` | the [MCP provider](/docs/agent/mcp) is registered in `adonisrc.ts`. A separate mount point, with its own identity path. |

## The routes

| # | Method & path | Purpose |
| --- | --- | --- |
| 1 | `POST /agent/chat` | Start a run. Resolves the actor, creates or continues a thread, and **streams the reply as SSE**. Body: `{ message, threadId?, agent?, persona?, attachments?, pageContext?, model? }` — `model` must be a catalog model available to the caller (`400` otherwise). |
| 2 | `GET /agent/chat/:runId/stream` | **Re-attach** to a run's live token stream (reconnect / resume). |
| 3 | `POST /agent/chat/:runId/cancel` | Abort a run. Returns `{ aborted: true }`. |
| 4 | `POST /agent/tool-call/approve` | Approve a pending `action` tool call. Body: `{ toolCallId, runId? }`. |
| 5 | `POST /agent/tool-call/reject` | Reject a pending `action` tool call. Body: `{ toolCallId, runId?, reason? }`. |
| 6 | `GET /agent/threads` | List the actor's threads. |
| 6c | `GET /agent/models?agent=` | The models the caller may pick: `{ providers: [{ id, label, models: [{ id, label, description?, badges?, available, unavailableReason?, contextWindow? }] }], default }` — see [Models](#models). An empty catalog when none is configured. |
| 6d | `GET /agent/agents` | The registered agents for a picker: `{ name, description, isDefault? }[]`. |
| 6b | `GET /agent/tools?agent=` | The tools the caller can reach through an agent, as `{ name, kind, presentation? }[]` — the same list the model is offered. `404` for an unknown agent. See [Presentation](/docs/agent/authoring/tools#presentation--how-a-chat-surface-talks-about-a-tool). |
| 7 | `GET /agent/threads/personas/catalog` | The persona `{ id, label }` catalog for a UI picker. |
| 8 | `GET /agent/threads/:id` | Thread detail (messages + `activeRunId`, the run streaming right now or `null` — the one to re-attach to), or `null`. Thread summaries carry `activeRunId` too. |
| 8b | `PATCH /agent/threads/:id` | `{ title?, model? }` — rename (1–200 characters) and/or pin a catalog model on the thread (`null` unpins; `400` for a model the catalog does not offer, `501` on a store without `updateThread`). Answers `{ ok: true }`. |
| 8c | `POST /agent/messages/:id/feedback` | Rate a message: `{ value: 'up' \| 'down' \| null, comment? }` → `{ feedback: { value, comment?, updatedAt } \| null }` (`null` clears). Only the thread's owner — `403` otherwise; `404` unknown message; `400` a bad value; `501` on a store without `threadOfMessage` + `setMessageFeedback`. The rating comes back as `StoredMessage.feedback` and is not copied to a fork. |
| 9 | `DELETE /agent/threads/:id` | Soft-delete a thread. |
| 10 | `POST /agent/threads/:id/fork-from/:messageId` | Fork a thread up to a message (regenerate / branch). |
| 11b | `GET /agent/quota` | Every budget window with its usage — see [Budget windows](/docs/agent/governance/quota-and-cost#budget-windows). A send while one is exhausted answers `429` `{ code: 'quota_exceeded', period, message }`. |
| 11 | `GET /agent/config` | Server facts a client would otherwise repeat: `{ attachments: { enabled, upload, maxBytes, allowedContentTypes, maxPerMessage }, models: { enabled }, quota: { enforced }, identity: { anonymous } }` (what the React `useAgentConfig` reads). |
| 12 | `GET /agent/approvals/mine` <span data-opt>optional</span> | The **calling actor's own** pending HITL approvals, oldest first. Query: `limit?` (default `50`, clamped to `200`). Mounts with `governanceQueries` but is **not** behind `governanceAuthorize` — it is always scoped to `actor.id`, so a non-admin surface (e.g. a coordinator's chat) can poll its own suspended tool calls even when the cross-actor read-model is ADMIN-only. |

<Callout type="info" title="Every route resolves the actor first">
Routes that need identity — chat, threads list, quota — resolve the actor first. With no `actorResolver` configured each browser is its own anonymous actor (an HttpOnly `agent_anon` cookie set on its first request); with one, a resolver that throws makes the route reply `401` and never run. See [Authorization](/docs/agent/governance/authorization).
</Callout>

<Callout type="warn" title="Owner-scoped routes (IDOR protection)">
Routes addressed by a `runId` or `threadId` — stream, cancel, approve, reject, `threads/:id` (get/delete/fork), and continuing an existing thread on `chat` — additionally enforce **object-level ownership**: a caller may act only on the runs and threads it owns. A non-owner that guesses an id gets `404` (unknown) or `403` (not owner), unless it is governance-privileged. See [Object-level ownership](/docs/agent/governance/authorization#object-level-ownership).
</Callout>

The persona catalog route is registered *before* `threads/:id` so it isn't captured by the `:id` param.

## The SSE envelope

`POST /agent/chat` and `GET /agent/chat/:runId/stream` reply with `Content-Type: text/event-stream`. Which envelope the frames are written in is `streamProtocol` in `config/agent.ts`:

| `streamProtocol` | Wire | Read by |
| --- | --- | --- |
| `'legacy'` (default) | `data: {"delta":"…"}` per text chunk, plus named `event: component` / `event: elicitation` / `event: approval` frames | clients written against this package's original envelope |
| `'agent'` | one `AgentStreamEvent` JSON object per `data:` frame — the chat stream protocol shared with `@dudousxd/nestjs-agent` | `@dudousxd/nestjs-agent-react` (transport, `useAgentChat`, transcript model) unchanged, and `@adonis-agora/agent/client` |

`@adonis-agora/agent/client` reads both, so switching is a server-side change. The default stays `'legacy'` so an upgrade never changes the bytes an existing hand-written reader parses.

### `streamProtocol: 'agent'`

```text
event: meta
data: {"runId":"<uuid>","threadId":"<uuid>"}

data: {"kind":"step-start"}

data: {"kind":"reasoning","text":"The user wants…"}

data: {"kind":"tool-input-available","id":"c1","name":"weather","input":{"city":"Lisbon"},"toolKind":"read"}

data: {"kind":"tool-output","id":"c1","output":{"tempC":21}}

data: {"kind":"step-finish","usage":{"inputTokens":812,"outputTokens":40},"costUsd":0.0004}

data: {"kind":"step-start"}

data: {"kind":"text","text":"It is 21°C in Lisbon."}

data: {"kind":"step-finish","usage":{"inputTokens":870,"outputTokens":9},"costUsd":0.0001}

data: {"kind":"title","title":"Weather in Lisbon"}

event: done
data: {}
```

The vocabulary, field for field, is the NestJS library's [stream protocol](https://github.com/DavideCarvalho/nestjs-agent/blob/master/docs/stream-protocol.md) (`AgentStreamEvent`, exported from this package too). What this package writes:

| `kind` | When |
| --- | --- |
| `step-start` / `step-finish` | around each model call and the tools it asked for; `step-finish` carries `usage` and `costUsd` (`null` when unpriced, never a made-up `0`) |
| `text`, `reasoning` | as the model streams them (the AI SDK adapter streams reasoning deltas) |
| `tool-input-start` / `-delta` / `-available` | as the model streams a call; a provider that streams none gets its calls announced by the loop once the model call returns |
| `tool-output` / `tool-output-error` / `tool-output-denied` | once the step's tools have settled; a person's "no" is `tool-output-denied`, never an error |
| `elicitation` | a question set the run is parked on (plus `runId`, the run to answer against) |
| `approval-requested` | an `action` call parked on a person: `approver: 'requester'` (plus `runId`, `toolName`, `input`) |
| `ui` | a component a tool pushed with `ctx.emitUi` (or the older `ctx.emitComponent`) — `id` defaults to `<toolCallId>:ui:<n>`, a repeat replaces it; persisted on the message once the step's tools settle |
| `title` | the thread was titled from its first message |
| `cancelled` | the run was stopped — the last frame before `done`, so a truncated answer reads as one |

Every event frame carries an SSE `id:` — its 1-based position in the run (`id: 7` above `data: {"kind":"text",…}`). The number belongs to the frame, not the connection: the same frame has the same id on the `POST` that started the run and on every later `GET …/stream`. `GET /agent/chat/:runId/stream?after=<n>` (or the standard `Last-Event-ID` header; `after` wins) sends only the frames numbered above `n`, still preceded by `meta` — which is how the shared React client resumes a dropped stream without re-rendering what it has. `meta`, `done` and `error` carry no id. When nothing is buffered under the run any more (it ended while the client was away, or its buffer went with a restarted process), the route answers `404`, read as "nothing to resume"; a sink reports that through the optional `TokenStreamSink.has` (the in-process, in-memory and Redis sinks implement it).

A failed run ends with `event: error` + `data: {"code","message"}` instead of `done`; the codes are `quota_exceeded`, `output_rejected`, `structured_output_invalid` and `run_failed`.

Frames are written from inside the loop's existing checkpoints, so a durable replay never streams one twice and no checkpoint moved.

### `streamProtocol: 'legacy'`

```text
event: meta
data: {"runId":"<uuid>","threadId":"<uuid>"}

data: {"delta":"The "}
data: {"delta":"weather "}
data: {"delta":"in Lisbon is 21°C."}

event: done
data: {}
```

- A single **`meta`** frame first, carrying the `runId` and `threadId`.
- One **`data`** frame per streamed chunk, each `{"delta": "<text>"}`.
- A terminating **`done`** frame when the run completes. A failed run writes `{"delta":"\n[error] <message>"}` and then `done`.

Frames with no legacy spelling (reasoning, tool calls, steps, title) are not written.

<Callout type="info" title="Component frames (Generative UI)">
A tool can also emit a typed UI component into the stream, which appears as a named `event: component` frame (`data: {"name":...,"data":...}`) interleaved with the text `delta`s. The text envelope above is unchanged — text-only clients ignore the extra event. See [Generative UI](/docs/agent/generative-ui).
</Callout>

The response also sets `X-Agent-Run-Id` and `X-Agent-Thread-Id` headers (plus `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no` so proxies don't buffer the stream). The stream ends only on run **completion** — the token sink stays open across a HITL suspend, so an approved-then-resumed run keeps one continuous stream.

## Persisted history

`GET /agent/threads/:id` returns the messages a reload rebuilds the transcript from. Besides `content`, `toolCalls`/`toolResults` and `attachments`, an assistant message carries what its step streamed, so a reloaded thread shows what the live one did:

| Field | What it holds |
| --- | --- |
| `reasoning?: string` | the model's thinking for the step, as its `reasoning` frames streamed it |
| `reasoningMs?: number` | how long it thought — the sum of each burst of consecutive `reasoning` frames; the same number `step-finish` carries live |
| `ui?: { id, component, props, version?, toolCallId? }[]` | components the model turn pushed (`ui` frames), first-seen order, last props per `id` |

They are read off the frames inside the model call's own checkpoint, so a durable replay persists the same values rather than re-measuring a turn that is not happening. A provider may also report them itself on `ModelTurnResult` (`reasoning`, `reasoningMs`, `ui`); its values win. `@dudousxd/nestjs-agent-react`'s `storedThreadToUiMessages` replays them as `reasoning` and `data-ui` parts.

## Models

A turn's model is the send's `model`, else the thread's pinned model, else the provider's default. The simple way to offer a picker is `aiSdkModels` — several models behind one provider, which carries its own catalog:

```ts title="config/agent.ts"
import { aiSdkModels } from '@adonis-agora/agent/ai-sdk'
import { openai } from '@ai-sdk/openai'

export default defineConfig({
  model: () =>
    aiSdkModels(
      {
        'openai/gpt-4o-mini': { model: openai('gpt-4o-mini'), label: 'GPT-4o mini', badges: ['fast'] },
        'openai/gpt-4o': { model: openai('gpt-4o'), label: 'GPT-4o' },
      },
      { default: 'openai/gpt-4o-mini', providerLabels: { openai: 'OpenAI' } },
    ),
})
```

With no `models` in the config, `GET /agent/models` serves that catalog and a turn runs on the picked id. `aiSdkModel(model)` serves one model and refuses a pick naming another (the turn fails) rather than silently answering on a model nobody chose.

To decide per caller (plan, budget, provider health), set `models` to a `ModelCatalog` — `list({ actor, agent })` returns the same view, with `available: false` and an `unavailableReason` for what the caller cannot use right now — or to a literal view for a fixed list. The server refuses (`400`) any model the catalog does not list as available, on a send and when pinning — a client only ever sends ids the catalog listed, but the server does not trust that. The picked id reaches the provider as `ModelTurnArgs.model`. The pick rides the run's input, so a durable replay runs on the same model, and it labels the turn's usage when the provider reports no model id.

## Human-in-the-loop

When the model calls an `action` tool, the run records it `pending_approval` and pauses. The client learns the pending `toolCallId` from the thread detail (`GET /agent/threads/:id` → the tool call's status), then decides:

```bash
# approve
curl http://localhost:3333/agent/tool-call/approve \
  -H 'content-type: application/json' \
  -d '{"runId":"<runId>","toolCallId":"<toolCallId>"}'

# or reject, optionally with a reason fed back to the model
curl http://localhost:3333/agent/tool-call/reject \
  -H 'content-type: application/json' \
  -d '{"runId":"<runId>","toolCallId":"<toolCallId>","reason":"not this account"}'
```

On approve, the loop runs the tool and continues, recording who approved it. On reject, it records the rejection and feeds a rejection result back to the model, which continues the turn. A decision is always scoped to one `(runId, toolCallId)` pair, so one run can never approve another's call. `runId` may be omitted — a tool call id is unique, so the route reads the run off the call's own row (`AgentStore.getToolCallRunId`) and answers `404` for a call it does not know. That is the body `@dudousxd/nestjs-agent-react` sends; the same holds for `tool-call/answer` and `tool-call/skip`.

Both decision routes take two optional fields: `via` names the surface the decision came through (`'web'` when omitted, 1–64 characters) and `remember: true` (approve only) approves later calls of the same tool in the same thread without asking again. A malformed one is a `400`.

### Approval policy

By default the person chatting approves every `action` call, and a request never lapses. `approvalPolicy` in `config/agent.ts` changes who and for how long:

```ts title="config/agent.ts"
export default defineConfig({
  // …
  approvalPolicy: {
    ttlMs: 15 * 60_000, // every request lapses after 15 minutes
    tools: {
      refund: { approver: 'FINANCE' }, // a role decides refunds
      lookupInvoice: { required: false }, // an action that runs without asking
    },
  },
})
```

That shorthand covers most deployments. For a decision per actor, thread or agent, pass a whole `ApprovalPolicy` — `requirementFor(tool, actor, thread)` returns `{ required, approver, ttlMs? }`, and an optional `canDecide(actor, { toolCallId, approver, requesterRef })` replaces the default "holds that role" rule (plug an authz gate in there):

```ts
import { REQUESTER_APPROVER, type ApprovalPolicy } from '@adonis-agora/agent'

const approvalPolicy: ApprovalPolicy = {
  requirementFor: (tool, actor) =>
    tool.spec?.ability === 'billing.refund'
      ? { required: true, approver: 'FINANCE', ttlMs: 3_600_000 }
      : { required: true, approver: REQUESTER_APPROVER },
  canDecide: (actor, decision) => actor.roles?.includes(decision.approver) === true,
}
```

What changes on the wire and the routes:

- **Who.** `approval-requested` carries the `approver`. For the requester, the approve/reject routes keep the ownership check they always had. For any other approver the caller must pass `canDecide`, else `403` — including the person chatting.
- **Until when.** With a `ttlMs` the frame carries `expiresAt`, and the run waits at most that long: the inline runner arms a timer, the durable runner hands the time to its signal wait's own timeout (a deadline the runtime journals, so it survives a restart). Nobody deciding in time settles the call `expired`: `approval-settled { status: 'expired' }`, then `tool-output-denied` with reason `approval expired`, and the model is told the approval lapsed — not that someone said no. A decision on a lapsed request answers `410`.
- **How it settled.** `approval-settled` names `decidedBy`, `decidedVia` and `remember` (or `reason` on a rejection). A remembered approval streams `approval-settled { decidedVia: 'remembered' }` without asking.
- **History.** `GET /agent/threads/:id` returns each message's `approvals: [{ toolCallId, approver, expiresAt?, status, remember?, decidedBy?, decidedVia?, reason? }]`.

The requirement is decided inside the call's own `persist:toolcall` checkpoint, so a parked durable run keeps the answer it was given even if the policy changes while it waits. The Lucid store adds four nullable `agent_tool_call` columns for it (`approver`, `expires_at`, `remember`, `decided_via`); a custom `AgentStore` opts in with `rememberedApprovals` and `toolCallApproval` (both optional).

## Re-attaching to a run

Streams survive a dropped connection. A late subscriber to `GET /agent/chat/:runId/stream` replays the run's buffered chunks first, then follows live until `done`. Combined with the thread's `activeRunId`, a reloading client can find the in-flight run and rejoin its stream.

<Callout type="warn" title="Single-replica by default">
Re-attach works because the default token sink buffers per run in process memory. That makes it single-replica: a run started on one instance can only be re-attached on that same instance. Switch to the [Redis sink](/docs/agent/redis-streaming) so any pod can serve any run's stream, and pair it with the [durable runner](/docs/agent/durability/durable-runner) for cross-instance resume.
</Callout>

## Consuming the stream

The package ships the client. `@adonis-agora/agent/client` posts a turn, decodes the envelope above into typed frames, and re-attaches automatically when the connection drops; `@adonis-agora/agent/react` wraps it in a `useAgentChat` hook:

```tsx
import { useAgentChat } from '@adonis-agora/agent/react'

function Chat() {
  const { messages, status, error, send, cancel } = useAgentChat({ basePath: '/agent' })
  // messages[].parts is ChatPart[] — text and component parts in emission order
}
```

Both are covered in full — options, resume semantics, component frames, and the HITL calls the client deliberately leaves to you — in [Browser client & React](/docs/agent/browser-client).

For a non-JavaScript consumer, or a bespoke reader, the envelopes above are the whole contract: read `text/event-stream`, dispatch on the `event:` name, and read an unnamed event as a text `delta` (legacy) or an `AgentStreamEvent` dispatched on its `kind` (agent) — tolerating kinds you do not know. To use the NestJS library's React package against this server, set `streamProtocol: 'agent'`.
