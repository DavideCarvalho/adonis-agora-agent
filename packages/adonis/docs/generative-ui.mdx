A tool does not have to answer only in prose. It can push a **typed UI component frame** into the run's live stream — a weather card, a chart, a confirmation form — and the frontend renders your real React component in the transcript, right where the text would have gone. A client that cannot draw it declares so, and receives the component's text instead — see [One output, many surfaces](/docs/agent/surfaces).

Drawing the same components through CopilotKit or OpenUI instead of the native client is compared, row by row, in [Generative UI: native vs CopilotKit vs OpenUI](/docs/agent/frontends).

For result-driven UI, use the tool’s optional `present` hook. See [Component registries and server rendering](/docs/agent/authoring/component-rendering) for functional/class tools, custom components, shared React renderers, and WhatsApp image/PDF delivery.

## What it is (and when to reach for it)

The model streams text. Sometimes text is the wrong medium: "your glucose is trending up" is far weaker than an actual line chart, and "here's the weather" begs for a card with an icon and a temperature. **Generative UI** lets a tool emit a *structured component reference* — a `name` plus a JSON `data` payload — that the client maps to a component in its own registry and paints inline.

The split is deliberate:

- **The server decides *what* to show and *with what data*** — the tool computes the payload and emits `('WeatherCard', { city, tempC, condition })`. It never ships markup, HTML, or JSX over the wire.
- **The client decides *how* to render it** — it owns the `WeatherCard` React component and the styling. The server's `name` is just a key into that registry.

That keeps the trust boundary clean (no server-authored HTML executing in the browser) and lets the same run drive a rich web UI, a terminal renderer, or a mobile app from one stream.

<Callout type="info" title="Emit alongside text, not only instead of it">
A push doesn't replace the tool's return value or the model's prose. A tool can emit a component **and** return a text result to the model (so the model can keep reasoning about it) **and** the model can keep streaming text after. Component and text frames interleave in emission order — see [Interleaving](#interleaving-with-text).
</Callout>

Use it when the answer is inherently visual or interactive: metrics/charts, maps, media galleries, structured records (an order, an invoice), or a small inline form. Reach for plain text (or a plain [tool](/docs/agent/authoring/tools) return) when the answer is prose or a value the model needs to reason over.

## The whole path, end to end

<Steps>

<Step>

**A tool pushes a component** — `ctx.emitUi(component, props)` during `execute`, its `present` hook after it, or a `ui__show_*` tool the catalog registered. With a [catalog](#a-component-catalog--adonis-agoraagentgenui) configured the push is validated and negotiated against the client's [UI capabilities](/docs/agent/surfaces#ui-capabilities) first; a drawable one is written as a `{ t: 'component', name, data, id, toolCallId, … }` frame to the run's token stream at the current position.

</Step>

<Step>

**The sink carries the typed frame.** Text and component frames travel in the same token stream — the in-process sink buffers them for reconnect, the Redis and Lucid sinks share them across replicas. Frame-for-frame identical either way.

</Step>

<Step>

**The provider serializes each frame to SSE** in the agent stream protocol: a text frame becomes `{"kind":"text","text":...}`; a component frame becomes a `ui` event carrying `{ id, component, props, version?, fallbackText?, toolCallId? }`. Over [AG-UI](/docs/agent/ag-ui) it is the `agora.ui` custom event.

</Step>

<Step>

**The client switches on the event `kind`** — `text` events append text; `ui` events look up `component` in a component registry and render it with `props`.

</Step>

</Steps>

## Server side

### `ctx.emitUi(component, props, options?)`

The push to reach for. Every tool's context carries it — always present, a no-op outside a conversation (an MCP call), so a tool never branches on where it runs:

```ts
defineTool(
  { name: 'orders', kind: 'read', description: 'List recent orders', input: z.object({}) },
  async (_input, ctx) => {
    const columns = [{ key: 'id', label: 'Order' }, { key: 'status', label: 'Status' }]
    const { id } = await ctx.emitUi('DataTable', { columns, rows: [] }) // a placeholder
    const orders = await Order.query().select('id', 'status').limit(20)
    const rows = orders.map((order) => ({ id: order.id, status: order.status }))
    await ctx.emitUi('DataTable', { columns, rows }, { id }) // same id → replaced in place
    return { count: rows.length } // what the model reads
  },
)
```

- It streams at once as a `ui` event (`{ kind: 'ui', id, component, props, version?, fallbackText?, toolCallId }`).
- `id` defaults to `<toolCallId>:ui:<n>`; pushing an `id` again replaces that component rather than adding one. `props` must be a JSON object (it is snapshotted at the push). `version` names the props' schema version, so a client can keep rendering components an older server persisted. `fallbackText` is the text a client shows when it cannot draw the component.
- With `genui` configured, the push is checked against the catalog resolved for the request: the component must be defined there, a given `version` must be the definition's, and the props must pass its schema — otherwise `emitUi` throws. The server then stamps the definition's `version` and generates `fallbackText` from it (any `fallbackText` option is replaced). A component the client did not declare in its [UI capabilities](/docs/agent/surfaces#ui-capabilities) is streamed and persisted as text instead, and `emitUi` still resolves with its `id`.
- Once the step's tools have settled, every component they pushed is **persisted on the assistant message** (`StoredMessage.ui`, after what the model turn itself streamed), so `GET /agent/threads/:id` returns what the live stream showed. The pushes ride the tool step's journaled result, so a durable replay neither re-streams nor re-persists them. A custom `AgentStore` opts in with `setMessageUi` (optional).

### A component catalog — `@adonis-agora/agent/genui`

Instead of writing a tool per component, declare the components once and let the model push them. Agora owns the isomorphic, framework-free catalog in `@adonis-agora/agent/genui`, so the same definition file serves the server and the browser's `GenuiProvider` from `@adonis-agora/agent/react/genui`. No Aviary package is required:

```ts title="app/genui/catalog.ts"
import { defineCatalog, defineComponent } from '@adonis-agora/agent/genui'
import { BUILTIN_COMPONENTS } from '@adonis-agora/agent/genui/builtins'
import { z } from 'zod'

export const catalog = defineCatalog([
  ...BUILTIN_COMPONENTS, // DataTable, Chart, KpiCards, …
  defineComponent({
    name: 'OrderCard',
    title: 'Order card',
    description: 'One order at a glance.',
    props: z.object({ id: z.number(), status: z.string() }),
  }),
])
```

```ts title="config/agent.ts"
import { genui } from '@adonis-agora/agent/genui'
import { catalog } from '#genui/catalog'

export default defineConfig({
  model,
  genui: genui({ catalog }),
})
```

`BUILTIN_COMPONENTS` are ready-made definitions (no visuals) for a table, a chart, KPI cards, sources, a checklist, a timeline, code, a diff and a callout; `LAYOUT_COMPONENTS` adds `Stack`, `Card`, `Heading`, `Text`, `Badge`, `Link` and `Image` for tree mode. Each is listed with its props, and how to pick or override them, in [Builtin components](/docs/agent/genui-builtins).

That registers a `ui__show_<snake_case name>` tool per model-facing component (`OrderCard` → `ui__show_order_card`); each call validates its input against the catalog (a refused call reaches the model as a tool error it can fix) and pushes through `ctx.emitUi`. Component names are letters and digits starting with a letter (`/^[A-Za-z][A-Za-z0-9]{0,63}$/`); a definition marked `internal: true` is never offered to the model. Options, all optional:

| Option | Meaning |
| --- | --- |
| `mode` | `'per-component'` (default) or `'tree'` — one `ui__render` tool taking a nested `{ type, props, children }` tree, pushed as one `genui:tree` component. |
| `showTool` | `true` (or a tool name) adds a generic `ui__show` taking `{ component, props }` — how a model reaches components that exist only in a per-request catalog. |
| `terminal` | A successful push ends the turn. |
| `roles` | Roles allowed to call the tools; omitted → `defaultRoles`. |
| `presentation` | `(component) => ToolPresentation \| undefined`, overriding the generated chat copy per tool. |
| `namePrefix` | Prefix of the per-component tools. Default `ui__show_`. |
| `treeToolName`, `treeInstructions`, `treeLimits` | The tree tool's name (default `ui__render`), extra description, and size limits. |
| `showInstructions` | Extra description for the show tool. |

When a turn carries [UI capabilities](/docs/agent/surfaces#ui-capabilities), each tool describes only what the client can draw, and a component's tool is hidden from the model when it cannot. The catalog is bound in the container — `@inject() constructor(private genui: AgentGenui)` → `this.genui.catalog`.

**Per request.** A tenant with its own components, or its own version of one, is a resolver:

```ts
import { GenuiCatalogResolver, type GenuiCatalogScope } from '@adonis-agora/agent/genui'

export class TenantCatalogs extends GenuiCatalogResolver {
  async resolve({ actor }: GenuiCatalogScope) {
    return catalog.extend(await Tenant.componentsFor(actor.tenantRef))
  }
}

// config/agent.ts
genui: genui({ catalog, resolver: TenantCatalogs, showTool: true })
```

A resolver class is built through the container (so it can `@inject()`); an instance or a plain `(scope) => catalog` works too. Calls validate against the resolved catalog, and each turn's tool descriptions come from it — through `ToolHandler.describe`, a hook any tool can implement to vary what the model is told per actor, thread or agent.

### Terminal tools

A tool whose effect IS the answer — it pushed the UI the user reads — can end the turn: `terminal: true` on `defineTool` / `@AiTool` / `static tool`. Once such a call succeeds no further model call narrates it; a failed one does not end the turn, so the model can recover.

```ts
defineTool({ name: 'showChart', kind: 'read', description: '…', input, terminal: true }, async (input, ctx) =>
  ctx.emitUi('Chart', await chartFor(input)),
)
```

`ctx.emitComponent(name, data)` below is the older form. It still works — and now goes through the same path, so its components are validated, negotiated and persisted too.

### `ctx.emitComponent(name, data)`

Every tool handler's second argument is an [`AiToolCtx`](/docs/agent/authoring/tools#the-tool-context). Under the agent loop it also carries the older push:

```ts
emitComponent?(name: string, data: unknown): void | Promise<void>
```

- **`name`** — the component name, a key the client resolves to a component. With a catalog configured it must be a catalog component, so use the same identifier rules (`'WeatherCard'`, `'TrendChart'`).
- **`data`** — the props. A JSON object is pushed as is; any other value is wrapped as `{ value: data }`. Keep it serializable: no class instances, no functions, no circular references.

It is `ctx.emitUi(name, data)` without options and without the returned id.

<Callout type="warn" title="Call it through the optional chain">
`emitComponent` is **optional** on `AiToolCtx` — the agent loop wires it, but other contexts (an [MCP](/docs/agent/mcp) call, a test, a direct `registry.invoke`) omit it. Call it as `ctx.emitComponent?.(...)`, or use `ctx.emitUi`, which is always present and does nothing where there is no conversation.
</Callout>

Here is a `ReadTool` that emits a weather card and *also* returns a text summary to the model — so the model can narrate around the card:

```ts title="app/agent_tools/get_weather.ts"
import { ReadTool } from '@adonis-agora/agent'
import type { AiToolCtx } from '@adonis-agora/agent'
import { z } from 'zod'
import WeatherService from '#services/weather_service'
import { inject } from '@adonisjs/core'

const input = z.object({ city: z.string() })
type Input = z.infer<typeof input>

interface WeatherCard {
  city: string
  tempC: number
  condition: 'sunny' | 'cloudy' | 'rain'
  humidity: number
}

@inject()
export default class GetWeather extends ReadTool<Input, { tempC: number }> {
  constructor(private readonly weather: WeatherService) {
    super()
  }

  static tool = {
    name: 'get_weather',
    description: 'Current weather for a city. Renders a weather card.',
    input,
  }

  async execute({ city }: Input, ctx: AiToolCtx) {
    const w = await this.weather.current(city)

    // 1) Push the UI component into the stream at this position.
    const card: WeatherCard = {
      city,
      tempC: w.tempC,
      condition: w.condition,
      humidity: w.humidity,
    }
    await ctx.emitComponent?.('WeatherCard', card)

    // 2) Still return a text result so the model can reason about / narrate it.
    return { tempC: w.tempC }
  }
}
```

<Callout type="info" title="Works from any tool shape">
`emitUi` and `emitComponent` live on the ctx, not on a base class — so they work identically from a [`@AiTool` class, a `BaseTool`/`ReadTool`/`ActionTool` subclass, or a `defineTool` function](/docs/agent/authoring/tools). An `action` tool's `execute` runs only after approval, so what it pushes arrives with the result; the approval card itself is worded by `presentation.confirm` or a preflight `confirmation` ([Action preflight](/docs/agent/authoring/tools#action-preflight)).
</Callout>

### The typed stream frame

The transport is a discriminated union — the "data plane" that carries live output decoupled from the durable control plane:

```ts
// from @adonis-agora/agent — the two arms generative UI uses
export type StreamFrame =
  | { t: 'text'; v: string }
  | {
      t: 'component'
      name: string
      data: unknown
      id?: string // `<toolCallId>:ui:<n>` unless the push named one
      toolCallId?: string
      version?: number
      fallbackText?: string
      componentVersions?: Record<string, number> // per node type, on a `genui:tree` push
    }
  | { t: 'event'; event: AgentStreamEvent } // …and the error, elicitation and approval frames
```

A push is written as `{ t: 'component', name: 'WeatherCard', data: card, id, toolCallId, … }` to the run's `SinkWriter`. Text tokens from the model — and the text of a component the client could not draw — are the `{ t: 'text'; v }` arm. Both flow through the same [`TokenStreamSink`](/docs/agent/streaming-and-http#re-attaching-to-a-run) — so component frames get the same buffering/replay guarantees as text: a late subscriber that re-attaches replays every component frame emitted so far, in order, before following live.

### The `ui` stream event

`AgentSseEncoder` (exported) writes each frame as the `AgentStreamEvent`s it stands for. A component frame becomes a `ui` event carrying its `version`, `fallbackText`, `componentVersions` and `toolCallId` when set; one that carries no data object is wrapped as `{ value: data }`, and one buffered without an id is numbered by its position (`ui:<n>`) so a replay replaces rather than duplicates it.

So a run that emits a weather card mid-sentence produces this on the wire (`POST /agent/chat` or `GET /agent/chat/:runId/stream`):

```text
event: meta
data: {"runId":"7f3…","threadId":"a12…"}

id: 1
data: {"kind":"text","text":"The weather in "}

id: 2
data: {"kind":"text","text":"Lisbon:"}

id: 3
data: {"kind":"ui","id":"c1:ui:0","component":"WeatherCard","props":{"city":"Lisbon","tempC":21,"condition":"sunny","humidity":48},"version":1,"fallbackText":"*Lisbon* 21°C, sunny","toolCallId":"c1"}

id: 4
data: {"kind":"text","text":" Looks like a nice day."}

event: done
data: {}
```

The key facts a client relies on:

- **Every frame is an `AgentStreamEvent`** dispatched on `kind` — `text`, `ui`, and the rest of the shared vocabulary. A reader skips kinds it does not know.
- **A `ui` event carries `{ id, component, props }`**, plus `version` and `fallbackText` when a catalog is configured; a second `ui` with the same `id` replaces the first in place.
- **Order is preserved** — the event lands exactly where `emitUi`/`emitComponent` was called relative to the surrounding text.

## Client side

The server never sends markup, so you own every pixel. You supply one thing — a **registry** mapping each component name to the React component that renders its props.

### In React

`@adonis-agora/agent/react/genui` draws pushed components with your renderers. Hand the registry to the provider once; every `ui` block of the transcript is then one `<GenerativeUI>`:

```tsx title="inertia/pages/chat.tsx"
import { AgentProvider, useAgentChat } from '@adonis-agora/agent/react'
import { GenerativeUI, type GenuiRegistry } from '@adonis-agora/agent/react/genui'
import { WeatherCard } from '~/components/weather_card'
import { TrendChart } from '~/components/trend_chart'
import { catalog } from '#genui/catalog' // optional: the file the server uses — props are validated before drawing

const registry: GenuiRegistry = { WeatherCard, TrendChart }

export default function ChatPage() {
  return (
    <AgentProvider genui={{ registry, catalog }}>
      <Chat />
    </AgentProvider>
  )
}

function Chat() {
  const { transcript } = useAgentChat()
  return transcript.items.map((item) => (
    <article key={item.id} data-role={item.role}>
      {item.blocks.map((block) => {
        if (block.kind === 'text') return <p key={block.key}>{block.text}</p>
        if (block.kind === 'ui') return <GenerativeUI key={block.key} part={block} />
        return null
      })}
    </article>
  ))
}
```

A component the registry does not know, props the catalog refuses, or a renderer that throws renders your `fallback` — or, without one, the item's `fallbackText` (nothing when it has none). A name is a lookup, never something to evaluate. A repeated `id` replaces the component in place, and a reloaded thread draws the same components from the message's persisted `ui` list. To tell the server what this registry can draw, pass `uiCapabilities` to `<AgentProvider>` — see [One output, many surfaces](/docs/agent/surfaces#web--react-over-the-native-stream). See [React](/docs/agent/react) for the rest of the hook.

### Without React

The framework-free client decodes the same frames into parts. `foldPart` is a pure reducer over them:

```ts
import { createAgentChatClient } from '@adonis-agora/agent/client'
import type { ChatPart } from '@adonis-agora/agent/client'

const client = createAgentChatClient({ basePath: '/agent' })

await client.send({
  body: { message: 'How is my glucose trending?' },
  onParts: (parts: ChatPart[]) => paint(parts),
})

function paint(parts: ChatPart[]) {
  for (const part of parts) {
    if (part.type === 'text') appendText(part.text)
    else mountComponent(part.name, part.data, part.fallbackText)
  }
}
```

`onParts` fires on every frame with the message rebuilt from scratch, so `paint` can be a plain re-render rather than a diff. A re-attach after a dropped connection replays the run from its first frame — including every component frame — so the rebuilt transcript is always complete.

## Interleaving with text

Component and text frames land in **emission order**. A tool that emits a card between two sentences streams `text → component → text`, and the sink preserves that exact ordering through buffering, replay, and the Redis multi-replica transport. A quick end-to-end shape:

```ts
// inside a tool's execute:
// (the model has already streamed "olha ")
await ctx.emitUi('TrendChart', { series, unit: 'mg/dL' })
// (the model then streams "tá subindo")
```

yields, frame for frame:

```text
data: {"kind":"text","text":"olha "}
data: {"kind":"ui","id":"c1:ui:0","component":"TrendChart","props":{"series":[...],"unit":"mg/dL"},"toolCallId":"c1"}
data: {"kind":"text","text":"tá subindo"}
```

The client appends `"olha "`, drops the chart component into the transcript, then appends `"tá subindo"` after it — a chart embedded mid-sentence, exactly where the tool put it.

## A second example — a chart

Server: a tool that computes a series and emits a `TrendChart` component (payload only — the client owns the SVG/canvas).

```ts title="app/agent_tools/glucose_trend.ts"
import { ReadTool } from '@adonis-agora/agent'
import type { AiToolCtx } from '@adonis-agora/agent'
import { z } from 'zod'

const input = z.object({ metric: z.enum(['glucose', 'weight']), days: z.number().int().default(30) })
type Input = z.infer<typeof input>

export default class GlucoseTrend extends ReadTool<Input, { points: number }> {
  static tool = {
    name: 'glucose_trend',
    description: 'Plot a health metric over time as a chart.',
    input,
  }

  async execute({ metric, days }: Input, ctx: AiToolCtx) {
    const series = await readSeries(ctx.actor.id, metric, days) // [{ t, v }, …]

    await ctx.emitUi('TrendChart', {
      series,
      unit: metric === 'glucose' ? 'mg/dL' : 'kg',
      label: metric,
    })

    // Return a compact summary the model can talk about.
    const latest = series.at(-1)?.v
    return { points: series.length, latest }
  }
}
```

Client: the `TrendChart` entry in the registry renders your real chart component with the emitted `series`/`unit` — nothing about the chart's implementation crosses the wire, only its data.

## Testing it

A push writes to the same sink you already assert against in [tool/loop tests](/docs/agent/testing). Emit from a fake tool and drain the sink — component frames come out typed and in order:

```ts
const sink = new InProcessTokenStreamSink()
const w = await sink.open('r1')
await w.write({ t: 'text', v: 'olha ' })
await w.write({ t: 'component', name: 'TrendChart', data: { unit: 'mg/dL' } })
await w.write({ t: 'text', v: 'tá subindo' })
await w.end()

const frames = []
for await (const f of sink.subscribe('r1')) frames.push(f)
// → [ {t:'text',v:'olha '}, {t:'component',name:'TrendChart',data:{unit:'mg/dL'}}, {t:'text',v:'tá subindo'} ]
```

And at the wire level, `frameToEvents(frame, position)` is a pure function — assert the exact events without booting HTTP:

```ts
frameToEvents({ t: 'component', name: 'card', data: { a: 1 } }, 0)
// → [{ kind: 'ui', id: 'ui:0', component: 'card', props: { a: 1 } }]
```
