Two seams decide access — the **actor resolver** (who is calling) and the **roles policy** (what they may do). With neither configured the agent is a free public chat: every browser is its own anonymous actor and every tool without `roles` is callable. One line each tightens it.

## The actor resolver — who is calling

Every request resolves to an `Actor` (`{ id, roles?, tenantRef? }`) through the configured `ActorResolver` — the identity seam.

<Callout type="warn" title="No resolver: the endpoints are public">
When `config/agent.ts` sets no `actorResolver`, the provider installs `AnonymousActorResolver` and says so at boot. Each browser gets its own identity: on its first request the response sets `agent_anon=<32 random bytes, base64url>; Path=/; Max-Age=31536000; HttpOnly; SameSite=Lax` (plus `Secure` over HTTPS), and the actor is `{ id: 'anon:' + SHA-256(token), roles: ['anonymous'] }`. Threads, quota and attachments belong to that id, so visitors never see each other's. The cookie is `HttpOnly` (page scripts cannot read it), server-minted and needs no secret. The identity contract remains compatible with Aviary. Set a `quota` for a public deployment — model spend is otherwise unbounded, per browser.

To require login, one line: `actorResolver: new AuthActorResolver()`. A route whose actor can't be resolved then replies `401` and never runs the model.
</Callout>

The resolvers that ship:

- **`AnonymousActorResolver`** — the default described above. Options: `cookieName`, `maxAgeDays`, `sameSite` (`'none'` for a cross-site client, which forces `Secure`), `secure`, `path`, `roles`.

- **`AuthActorResolver`** (recommended) — reads Adonis's authenticated principal off `ctx.auth.user` (populated by `@adonisjs/auth`). The agent routes run no auth middleware, so when no guard has tried the request yet it calls `ctx.auth.check()` itself — a session cookie or an access token works with no middleware; `guards: ['web', 'api']` checks those guards in order (`checkUsing`) instead of the default one. Fail-closed: throws (`401`) when no user is authenticated. Pass a `toActor` mapper when your user model doesn't expose `id` / `roles` / `tenantRef` directly:

  ```ts
  new AuthActorResolver({
    toActor: (user) => ({
      id: String(user.id),
      roles: user.roleNames, // e.g. pulled from a relation
      tenantRef: user.tenantId,
    }),
  })
  ```

- **`HeaderActorResolver`** (demos / gateways) — trusts `x-actor-id` (required), `x-actor-role` (comma-separated → `roles`), and `x-tenant-ref`. It throws when `x-actor-id` is absent and grants **no** default role (missing `x-actor-role` → `roles: []`, i.e. no tools). Only safe behind a gateway that strips and re-sets these headers from a verified principal.

- **`UnconfiguredActorResolver`** — throws on every request: an explicit "nobody" for a surface that must never serve anonymously.

You can also implement `ActorResolver` yourself — it's a one-method interface, `resolve(req): Actor | Promise<Actor>`.

## The roles policy — what they may do

Tool authorization is a `RolesPolicy` — `can(actor, tool): boolean | Promise<boolean>`. The default binding is `DefaultToolAuthorizer`:

- **Open unless restricted.** A tool that declares no `roles` takes `defaultRoles`, which is `[]` — no restriction — unless you set it. `action` tools still park on approval regardless (for an anonymous visitor that is a confirmation, since the requester approves). `defaultRoles: ['ADMIN']` restores the old fail-closed posture.
- **Set intersection.** Otherwise authorization is `actor.roles ∩ (tool.roles ?? defaultRoles) ≠ ∅`. Give a tool `roles: ['ADMIN']` to restrict it.

Configure it via `defaultRoles`, or swap the whole policy via `authorizer` (aliased `rolesPolicy`):

```ts title="config/agent.ts"
export default defineConfig({
  // ...
  defaultRoles: ['STAFF'], // roles a tool requires when it declares none
})
```

### Closing the empty list

An empty roles list means **open**: `roles: []`, `defaultRoles: []` and `registerFunctionalTool(registry, tool, [])` all let every resolved actor through. If your app uses an empty list to deny — a `roles` computed from permissions that can come out empty, a multi-tenant MCP server — keep it closed with `emptyRoles: 'deny'`:

```ts title="config/agent.ts"
export default defineConfig({
  // ...
  emptyRoles: 'deny', // an empty roles list reaches nobody
})
```

Closed, the actor needs a role the tool declares: a tool with no `roles` and no `defaultRoles`, or with an explicitly empty list, is neither offered nor invocable, and an actor with no roles reaches nothing. `defineMcpConfig` takes the same key. Building the policy yourself, it is `new ClosedRolesPolicy(defaultRoles)` / `new ClosedToolAuthorizer(defaultRoles)`, or `{ emptyRoles: 'deny' }` as the second argument of `DefaultRolesPolicy` / `DefaultToolAuthorizer`. The default stays `'allow'`.

## The double check

Authorization runs **twice** through the same `can(actor, tool)`, which is what makes it defense-in-depth:

1. **Offered-tools filter.** Before each model turn, `ToolRegistry.definitionsFor(actor, policy, allowedTools)` drops every tool the actor's role can't invoke — so a forbidden tool is never even described to the model. The persona/agent allow-list is applied on top as a second filter layer.
2. **Invoke-time re-check.** When the loop actually runs a tool, `ToolRegistry.invoke` re-checks `policy.can(...)` (and re-validates the input schema) before calling the handler. Even if a tool leaked into a call, it's refused with `ToolForbiddenError`.

Two per-tool gates sit around the policy on both layers: `enabled` / `isEnabled()` runs **before** it (a disabled tool is absent, and invoking one raises `ToolDisabledError`), and the tool's own `canUse(actor)` runs **after** it, for a per-actor decision the app-wide policy cannot express. Neither can widen what the policy allows. See [Turning a tool off, and gating it per user](/docs/agent/authoring/tools#turning-a-tool-off-and-gating-it-per-user).

<Callout type="info" title="One policy, both layers">
Both checks call the same `can(actor, tool)`, so swapping the policy — for the ability-aware authz adapter, or your own — changes offer and invoke together. They can never disagree about what an actor may reach.
</Callout>

## Ability-aware authorization

Every tool can also declare an `ability` (e.g. `'refund.issue'`). The default role-based policy ignores it, but an *ability-aware* `RolesPolicy` consults it — and one ships: the [`@adonis-agora/authz`](/docs/authz) Bouncer adapter, `authzToolAuthorizer`, which checks each tool's `ability` through authz, tenant-scoped and fail-closed. Because `can` may return a promise, the async authz check drops straight into the same seam — both filter layers pick it up. Swap it in via `authorizer`; see [Authz (Bouncer) adapter](/docs/agent/governance/authz-bouncer). `roles` and `ability` share the SPI, so you can declare abilities now and switch the policy anytime.

## Object-level ownership

Role and ability gate *which tools* an actor may call. They say nothing about *which records* an actor may address — and a chat run or a thread **is** a record, keyed by a `runId` / `threadId`. Without a second check, any authenticated caller who learns (or guesses) another actor's `runId` could re-attach to that run's live token stream, cancel it, or deliver a HITL approval on its behalf; a `threadId` could load a victim's full conversation history back over SSE, or append the caller's own turn into someone else's thread. That is a textbook **IDOR** (insecure direct object reference), and `0.6.0` closed it.

Every per-actor route now runs an **object-level ownership check** after resolving the actor and before touching the record. The decision core is the router-free `evaluateOwnership`, exported so you can unit-test it (or reuse it) without booting an app:

```ts
import { evaluateOwnership } from '@adonis-agora/agent'
import type { OwnershipVerdict } from '@adonis-agora/agent'

// evaluateOwnership(actorId, ownerRef, privileged): OwnershipVerdict
evaluateOwnership('u_1', 'u_1', false)  // → { ok: true,  status: 200 }  (the caller owns it)
evaluateOwnership('u_2', 'u_1', false)  // → { ok: false, status: 403 }  (someone else's record)
evaluateOwnership('u_2', null, false)   // → { ok: false, status: 404 }  (unknown / not owned)
evaluateOwnership('u_2', 'u_1', true)   // → { ok: true,  status: 200 }  (governance-privileged)
```

The three outcomes are deliberate:

| `ownerRef` | `privileged` | Verdict | Why |
| --- | --- | --- | --- |
| `=== actorId` | any | `{ ok: true, status: 200 }` | The caller owns the record. |
| `=== null` | any | `{ ok: false, status: 404 }` | Unknown record — reply `404`, **not** `403`, so the response never confirms to a non-owner that an id they don't own exists. |
| someone else's | `false` | `{ ok: false, status: 403 }` | Not the owner, not privileged. |
| someone else's | `true` | `{ ok: true, status: 200 }` | A cross-actor privileged caller (see below) may act across actors. |

On every owner-scoped route the request is checked before the handler runs: the record's owner is looked up, `privileged` is computed by running the console's `dashboard.authorize` — the same check the governance read-model uses, and `evaluateOwnership` produces the verdict. On a non-`ok` verdict the request is answered with the verdict's status (`404` → `"<kind> not found"`, `403` → `"forbidden"`) and the handler never runs.

<Callout type="info" title="Which routes are owner-scoped">
`POST /agent/chat` (only when continuing an existing `threadId`), `GET /agent/chat/:runId/stream`, `POST /agent/chat/:runId/cancel`, `POST /agent/tool-call/approve`, `POST /agent/tool-call/reject`, `GET /agent/threads/:id`, `DELETE /agent/threads/:id`, and `POST /agent/threads/:id/fork-from/:messageId` all enforce ownership. A **new** chat (no `threadId`) has no owner to check; the actor-scoped list routes (`GET /agent/threads`, `GET /agent/quota/today`) are already filtered to `actor.id`.
</Callout>

<Callout type="warn" title="Without authorize, ownership is strict">
`privileged` is `true` only when `dashboard.authorize` is configured **and** allows this actor. Without it, `privileged` is always `false` — so ownership is strict and even an admin can only touch its own runs and threads through these routes. Any denial (whatever its `reason`) just means "not privileged", and ownership decides.
</Callout>

## Governance route authorization

The cross-actor [governance read-model](/docs/agent/governance/read-model) — `/agent/governance/*` — exposes *every* actor's spend, usage, threads, runs, and pending approvals. It is not per-actor data, so ownership doesn't apply; instead it runs the console's `authorize`, the one option that also gates the [governance console](/docs/agent/governance/dashboard#access):

```ts title="config/agent.ts"
import { defineConfig } from '@adonis-agora/agent'
import { authorizeByRoles } from '@adonis-agora/authz'

export default defineConfig({
  // ...
  dashboard: {
    authorize: authorizeByRoles({ roles: ['ADMIN'] }),
    // or: authorize: (ctx, actor) => actor?.roles?.includes('ADMIN') ?? false,
  },
})
```

- **Omitted:** the routes are open while the app is not in production; in production every `/agent/governance/*` request answers `403 { "error": "forbidden" }`, and the app logs one warning at boot.
- **Set:** it decides with `ctx` and the resolved actor (optional — `undefined` when the request has none, e.g. a machine caller using `authorizeByToken`). `false`, `{ allowed: false }` and `reason: 'forbidden'` answer `403 { "error": "forbidden" }`; `reason: 'unauthenticated'` answers `401 { "error": "unauthenticated" }`; `{ redirectTo }` redirects a page navigation and answers `401 { "error": "unauthenticated", "redirectTo" }` to an API call; a throw answers `403`. See [the authorize contract](/docs/agent/governance/dashboard#the-authorize-contract) for the three forms (function, class, lazy import).
- `GET /agent/approvals/mine` is **never** gated by it: it is always scoped to the calling actor's own pending approvals, so a non-admin surface can poll its own approvals even while the cross-actor read-model is ADMIN-only.

<Callout type="warn" title="A thrown message never reaches production clients">
When `authorize` throws, the `403` body carries the error's message as `detail` **only outside production**. In production it is always `{ "error": "forbidden" }`, because an authorization predicate routinely throws with details a caller must not see.
</Callout>

`evaluateGovernanceGate` is exported for tests and for gating your own routes with the same `authorize`:

```ts
import { evaluateGovernanceGate } from '@adonis-agora/agent'

// evaluateGovernanceGate(actor | undefined, ctx, authorize?, debug?): Promise<GovernanceGateVerdict>
const verdict = await evaluateGovernanceGate(actor, ctx, config.dashboard?.authorize, !app.inProduction)

if (!verdict.ok) {
  return ctx.response.status(verdict.status).json({ error: verdict.error })
}
```

It decides only from the `authorize` you pass: with none it answers `{ ok: true }`, so keep the production default yourself on a route of your own.

## Organizations

When `config/context.ts` turns tenancy on, the agent scopes everything by the active organization
(with authkit organizations, the one picked in the account menu). Nothing to write in the agent:

```ts title="config/context.ts"
export default defineConfig({
  tenancy: { enabled: true, kinds: ['organization'] },
})
```

- Every actor carries the organization as `tenantRef`, so new threads, runs and usage rows are
  stamped with it. An `actorResolver` that sets `tenantRef` itself wins.
- A thread or run of another organization answers `404` on every route (chat, stream, cancel,
  approve, delete, fork), and `GET /agent/threads` lists only the organization's threads. A caller
  with no organization sees only threads that have none.
- `AgentService.recordUsage(...)` stamps the organization when you name no `tenantRef`.
- [`quota: { per: 'tenant' }`](/docs/agent/governance/quota-and-cost#budgets) gives the organization one budget.

To keep the agent unscoped while other libraries follow the organization, set `tenancy: false` in
`config/agent.ts`. `tenancy: { nullRows: 'shared' }` also shows threads with no organization inside
every organization.

## What governance covers

- Which tools an actor's **role** may reach (this page).
- Which tools a **persona/agent** exposes — a second allow-list layer. See [Personas & agents](/docs/agent/authoring/personas-and-agents).
- Which tools need a **human** before they run — the `action` kind and HITL. See [Streaming & HTTP](/docs/agent/streaming-and-http#human-in-the-loop).
- Which **records** (runs, threads) an actor may address — object-level ownership (this page).
- Who may read the cross-actor **governance read-model** — `dashboard.authorize` (this page).
- How much an actor may **spend** — the daily quota, checked before the model runs. See [Quota & cost](/docs/agent/governance/quota-and-cost).
